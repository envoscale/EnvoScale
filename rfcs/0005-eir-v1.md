# RFC 0005: EIR version 1

- **Status:** Accepted (2026-11-11). Under the owner's standing instruction to decide open
  design questions by the brief's core principles: one semantics for compiled code, the
  script VM and `comptime` (brief §3.7, §4.1), and the simplest design Stage 1, written in
  Envo-Core, can implement and Stage 2 can optimize.
- **Author(s):** founding engineer
- **Affects:** EIR (`EnvoLang/spec/eir.md`), compiler, script runtime
- **Tracking:** [#29](https://github.com/envoscale/EnvoLang/issues/29), milestone M2

## Summary

EIR version 1 is a typed SSA form with **block parameters** instead of φ-nodes, **scalar
SSA values** with **aggregates in memory**, **explicit drops** and no ownership
constructs (the front end has checked and lowered them), **checked instructions** that
panic, and **abort-on-panic** with no unwinding. It has a deterministic text form, a
LEB128 binary form with the magic `EIR\0`, and a verifier. The full reference is
[`EnvoLang/spec/eir.md`](https://github.com/envoscale/EnvoLang/blob/main/spec/eir.md); this RFC records the decisions and why.

## Motivation

`EnvoLang/spec/eir.md` fixed EIR's requirements but left four questions to an M2 RFC: the
memory model, how ownership facts are represented, panic edges and unwinding, and the
binary encoding. Stage 1 cannot be written until they are settled (M2.6, M2.7), and every
later backend, optimizer and the script VM (M6) build on the answers.

## Guide-level explanation

You meet EIR when you run `envo build --emit eir` to see what the compiler made of your
code. A function is a list of blocks; each line computes one value:

```
func @Min(%0: i32, %1: i32) -> i32 {
^bb0:
  %2 = cmp.gt i32 %0, %1
  condbr %2, ^bb1, ^bb2(%0)
^bb1:
  br ^bb2(%1)
^bb2(%3: i32):
  ret %3
}
```

`^bb2(%3: i32)` is a block that receives a value: whichever branch jumps there says what
`%3` is. Arithmetic says what happens on overflow: `add.chk` stops the program with
`panic: integer overflow`, `add.wrap` wraps around. Nothing in EIR is left undefined for
safe code, which is why a program gives the same answer compiled and as a script.

## Reference-level explanation

The normative text is [`EnvoLang/spec/eir.md`](https://github.com/envoscale/EnvoLang/blob/main/spec/eir.md) §1–§8. The decisions:

1. **Memory model: scalars in SSA, aggregates in memory** ([eir.model.3]). Only scalar
   types are SSA values; structs and arrays live in slots, globals or the heap and are
   accessed through pointers, and aggregate arguments and results are lowered to
   pointers. Pointers are untyped (`ptr`).
2. **Ownership: post-ownership EIR** ([eir.model.2]). Borrow checking and drop
   elaboration run on the typed syntax tree before lowering. EIR sees moves as copies,
   borrows as pointers, and drops as explicit calls guarded by drop flags. `slot.end`
   carries the one ownership fact the backend needs: where storage dies.
3. **Panics abort, no unwinding** ([eir.model.4]). Checked instructions and the `panic`
   terminator end the process with exit code 101 and the reason on standard error,
   exactly like Stage 0. Panic reasons are a closed, numbered list ([eir.panic.1]).
4. **Control flow: block parameters** ([eir.ssa.2]), not φ-nodes.
5. **Binary form** ([eir.bin.1]): magic `EIR\0`, a `u16` version, then id-tagged,
   length-prefixed sections (strings, target, types, globals, functions), LEB128
   integers, and opcodes numbered as part of the version. Text and binary round-trip
   exactly.
6. **Target in the header** ([eir.model.6]): sizes and offsets are computed for one
   target, named in the first line.
7. **Defined behaviour for safe code** ([eir.model.5]): wrapping, checked, shift,
   division and float-to-int conversions are all fully specified, and NaN results are
   canonical, so AOT, the VM and `comptime` agree.

## Drawbacks

- Keeping aggregates in memory means early EIR is load/store heavy. The Stage 2 optimizer
  has to promote slots to SSA values (scalar replacement) to get good code; Stage 1 does
  not optimize and does not care.
- Abort-on-panic means a panicking thread or task takes down the process. Recoverable
  panics for servers (catching at a task boundary) need unwinding, which a later version
  can add as new terminators without changing existing ones.
- Lowering drops before EIR means EIR passes cannot reason about ownership. Any
  ownership-aware optimization (for example eliding a copy-then-drop) must happen in the
  front end or be re-derived from `slot.end` and calls.

## Alternatives

- **φ-nodes.** Equivalent in power; block parameters make branch arguments
  explicit, are easier to print, parse and verify, and avoid the "φ at the top of the
  block" special cases.
- **First-class aggregate values in SSA.** Better for optimization, but the Stage 1
  backend, the VM and every pass would have to handle values of any size.
- **Ownership in EIR** (moves, borrows and drops as instructions). Enables more optimizations, but doubles the size of the IR and the verifier
  for Stage 1, which must stay small. A future "high EIR" above this one can add it.
- **Unwinding from v1.** Needs landing pads, cleanup blocks and an unwinder in every
  runtime, for no benefit to Stage 1 or the compiler itself.


## Unresolved questions

- Atomics and memory ordering, needed for threads (M4).
- SIMD vector types, needed by `envor.math` and AI kernels (M12).
- Debug information (source positions per instruction) for the debugger (M13); the text
  form will gain a `@line` annotation.
- Unwinding and recoverable panics at task boundaries.

## Migration / edition impact

None; this is the first version. [eir.ver.1] defines how later versions migrate.
